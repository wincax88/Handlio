# 部署与恢复

生产基础已部署到 Sealos；新增代码的部署结果以对应发布流水线为准。对外收费仍需要完成实际供应商、经营信息及商业验收。当前单实例部署不代表已达到 PRD 的全部可用性或恢复目标。

## 应用配置

1. 使用 Node.js 22.13+，`npm ci` 后执行 `npm run build`。
2. 复制 `.env.example`，配置 HTTPS `APP_ORIGIN` 和随机 `SESSION_SECRET`（至少 32 字符）。环境文件不能进入 Git。
3. 设置 `NODE_ENV=production`、Resend API Key（或 SMTP）和经认证的通知 / 验证码发信地址。生产验证码不会显示在页面。
4. 需要真实支付时配置已经完成主体审核的受控支付适配器、密钥及 Webhook Secret。按 `providers.md` 完成权威对象核验和真实订单 / 退款 / 结算验证。
5. AI 仅在实际供应商、处理协议、告知和质量样例完成后开启。无 AI 时手工路径完整。
6. 设置 `CHROMIUM_EXECUTABLE_PATH` 或安装 Playwright Chromium。保持浏览器更新；导出不允许网络请求或用户脚本。
7. `.data` 使用私有持久卷，禁止 Web Server 把目录作为静态资源。数据库、文件、备份与密钥采用平台提供的静态加密和独立权限。
8. `npm start` 提供 API 和 `dist`。TLS 由反向代理终止，外部只暴露 HTTPS。Origin 必须与浏览器地址一致。仅允许可信反向代理路径，不能为了通过代理随意关闭 CSRF 或验证码 IP 限流。

已提供 Docker 镜像、GitHub Actions 和 Sealos 单实例部署清单，见 [Sealos 部署操作](sealos.md)。当前不支持多实例共享 SQLite / 本地文件目录；数据库迁移、对象存储和 Worker 横向扩容需要单独设计。`tsx` 已归入生产依赖，运行镜像保留它。

## 备份

```powershell
npm run backup
```

设置 `BACKUP_KEY`（密钥管理器生成的 Base64 32 字节 AES 密钥）和 `BACKUP_DIRECTORY`（独立、私有的备份挂载目录）。应用每分钟检查是否距上次成功备份超过 24 小时；满足条件时创建加密 `.hbk` 快照并轮换超过 35 天的文件。密钥须独立保管，不进入 Git、日志或备份目录。未配置这两项时不会声称已开启自动备份。

SQLite 在线快照及 ready 图片以 AES-256-GCM 流式加密，归档含散列清单；导出可重新生成，不纳入备份。私有临时目录中的数据库快照在任务完成后清理。主数据库／图片卷仍需平台提供静态加密，独立目录也不等于已经异地复制。

删除请求后主内容在 7 天内清理；备份须在 35 天内轮换。不要以“不可变版本”作为无限保留正文的理由。真实账务记录按实际主体适用规则单独保留。

## 恢复演练步骤

在**独立新目录和独立服务环境**恢复，不能覆盖正在服务的 `.data`：

```powershell
npm run restore -- "C:/private-backups/handlio-example.hbk" "C:/restore-drill/new-data"
```

目标目录必须尚不存在，并位于当前 `DATA_DIR` 之外。工具先验证 GCM 认证，再按严格文件名、大小及总量约束解包，核对所有 SHA-256、SQLite 完整性；旧会话和验证码失效、共享暂停、未完成确认请求撤回，旧排队任务及通知取消，临时导出过期。解包使用 [yauzl 的逐项读取与文件大小验证](https://github.com/thejoshwolfe/yauzl)。

上线前，必须重新应用备份之后的删除墓碑、安全撤回、成员移除和分享撤销。先关闭全部共享和旧会话，取消旧任务 / 通知，再通过提供商重新核对订单、退款、争议及权益。验明状态后由 Owner 明确重新分享，不能因旧备份恢复自动开放客户内容。

已提供加密备份及独立目录恢复工具，并用虚构数据验证恢复、散列校验、篡改拒绝和会话撤销。实际异地备份、生产恢复、删除清单跨备份传播和 PRD RPO≤24 小时／RTO≤4 小时的生产环境验收仍需完成。

## 运行与告警

维护轮询每分钟处理到期提醒、免费草稿不活跃、临时导出过期、资产回收和主内容删除；进程必须持续运行。生产应监控 Worker 心跳，不能把进程停止时的轮询当作可靠定时调度。

监控项目：验证邮件失败、退信 / 投诉、未决订单、Webhook 死信、开权延迟、任务租约过期、导出失败、上传解码失败、存储、成本、授权拒绝突增和即将清理数据。当前 `/ops` 提供只含 metadata 的诊断；告警渠道和处理负责人需要外部设置。

已实现未决订单每日对账、Resend 退信 / 投诉回调、AI 成本预算与熔断，以及带 15 分钟冷却和审计的支付死信修复。对账由独立的每分钟轮询分批执行；仅查询原供应商会话，成功未决结果 24 小时后再查，失败 15 分钟后重试，调度状态和运行租约跨重启保留。`/ops` 可查看对账失败和死信，运营须近期验证并填写原因才能重试；重试入队不会直接发放权益。接口细节见 `api.md`。

这些代码需要随新版本部署才会在生产运行。实际供应商对账 / 投递、告警渠道及负责人、生产审计访问管理仍需验收。不得手工改快照、确认、交易金额或把数据库 `paid` 标记当作提供商付款证据。

## 收费前检查

- 全部 PRD P0 的 AC 逐项验收，26 类 TC 不能以当前测试数量替代。
- 真实邮件发送 / 验证 / 退信，支付成功、失败、延迟、重复、退款、争议、对账和结算。
- AI 30 组人工 / 对抗样例、处理协议、成本计量与熔断。
- 200 步、长截图、A4 / Letter、中文的导出基准和四种主要浏览器测试。
- 独立环境恢复、删除墓碑传播、备份轮换、稳定运行的清理和到期告警。
- WCAG 2.2 AA 审计、性能 / 并发基准、安全复核；当前只验证部分路径及 360px 浏览器视口。
- 正式经营主体、联系地址、支持邮箱、隐私 / 服务 / 退款政策与支付平台审核。
- 埋点口径、成本报表、业务验证和真实客户自助交接；不把演示 / 测试项目统计为有效外部交接。
